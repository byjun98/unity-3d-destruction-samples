## 프로젝트 개요

`3d_sample`은 게임에서 자주 보이는 부서짐, 무너짐, 번짐, 잘림 같은 연출을 Unity 기본 기능으로 만들어 본 개인 제작 샘플 프로젝트입니다. 외부 파괴 라이브러리에 맡기지 않고, Rigidbody, Collider, Joint, Mesh API, 머티리얼 제어를 조합해서 각 연출이 어떤 구조로 돌아가는지 확인하는 데 초점을 뒀습니다.

프로젝트에는 여섯 개의 데모가 들어 있습니다. 항아리나 박스처럼 한 번에 깨지는 오브젝트, 셀 단위로 번지는 불, 격자 기반 건물 파괴, 기둥 하중을 이용한 붕괴, 노드와 빔으로 만든 차량 변형, 런타임 메시 슬라이싱을 각각 분리된 씬과 코드로 구성했습니다.

| 구분 | 내용 |
| --- | --- |
| 장르 | Unity 3D 파괴 / 물리 / 메시 처리 샘플 |
| 엔진 | Unity 2022.3.62f3 LTS |
| 렌더링 | Universal Render Pipeline 14.0.12 |
| 언어 | C# |
| 주요 기술 | Rigidbody, Collider, Joint, Mesh API, Shader/Material 제어 |
| 주요 씬 | `Assets/Scenes/*.unity`, `Assets/Slicing/SlicingDemo.unity` |
| 공개 범위 | 직접 작성한 코드, 데모 씬, 샘플 머티리얼, 래퍼 프리팹 중심 |

## 방향성

이 프로젝트는 "정확한 물리 시뮬레이션"보다 "게임에서 보기 좋은 파괴 흐름"을 먼저 두고 만들었습니다. 실제 게임에서는 모든 것을 실시간으로 잘라내거나 계산하기보다, 데이터 상태를 바꾸고 그 결과에 맞춰 파편, 먼지, 사운드, 카메라 반응을 붙이는 경우가 많습니다.

그래서 각 데모도 같은 기준으로 나눴습니다.

- 가볍게 처리해도 되는 오브젝트는 미리 준비한 파편으로 교체합니다.
- 불은 파티클이 직접 번지는 것이 아니라 셀 데이터가 먼저 바뀌고, 파티클은 그 결과를 따라갑니다.
- 건물 파괴는 격자와 청크 단위로 계산해서 비용을 제한합니다.
- 붕괴는 한 프레임에 끝내지 않고 큐로 나눠 처리해 순서가 보이게 했습니다.
- 차량 변형은 풀 소프트바디 대신 적은 수의 노드와 빔으로 느낌만 잡았습니다.
- 메시 슬라이싱은 잘린 단면과 서브메시 보존을 직접 처리했습니다.

## 데모 흐름

```text
입력
  -> 발사, 클릭, 드래그, 충돌
  -> 각 데모의 좁은 진입점으로 전달
  -> HP, 온도, 하중, 노드 위치, 메시 절단 결과 갱신
  -> 파편, 청크, 불꽃, 먼지, 카메라 흔들림, HUD 갱신
```

각 데모는 입력과 시뮬레이션, 화면 표현을 가능한 한 분리했습니다. 예를 들어 발사체가 맞든, 클릭으로 데미지를 주든, 폭발 범위에 들어오든 실제 파괴 처리는 `TakeDamage`, `ApplyExplosion`, `ApplyImpact`, `TrySlice` 같은 작은 진입점으로 들어갑니다.

## 기술 상세

### 1. 모델 교체형 파괴

항아리, 박스, 유리창처럼 한 번 부서지면 끝나는 오브젝트는 런타임에 메시를 잘라내는 방식이 부담스럽습니다. 이 데모에서는 정상 모델과 파편 프리팹을 미리 준비해 두고, HP가 0이 되면 정상 모델을 끄고 파편을 같은 위치에 배치합니다.

구현 방식:

- `BreakableObject`가 HP와 파괴 상태를 관리합니다.
- `DemoImpactShooter`가 클릭이나 Space 입력을 받아 Raycast 또는 발사체 데미지를 전달합니다.
- `DestructibleMaterialTag`로 나무, 유리, 콘크리트 같은 재질 타입을 구분합니다.
- 파괴 시 파편 Rigidbody에 폭발 힘과 보조 방향 힘을 더해 흩어지게 합니다.

처리 포인트:

- 데미지를 받았는데 바로 깨지지 않는 경우에도 데칼, 먼지, 사운드로 반응을 보여줍니다.
- 파편이 바닥에 바로 박히지 않도록 위쪽 성분과 발사 방향 힘을 조금 섞었습니다.
- 머티리얼별 데미지 배율과 이펙트 차이를 따로 둘 수 있게 했습니다.

정리:

- 작은 환경 오브젝트는 사전 분할 프리팹 방식이 관리하기 쉽습니다.
- 플레이어가 보는 것은 "정확한 절단"보다 "맞았고, 금이 갔고, 결국 부서졌다"는 흐름입니다.

확장 방향:

- 아트 단계에서 파편 프리팹을 더 정교하게 만들면 코드 변경 없이 결과를 개선할 수 있습니다.
- 네트워크 게임에서는 파괴 여부와 파편 시드 정도만 동기화하고, 파편 물리는 클라이언트 연출로 둘 수 있습니다.

### 2. 그리드 기반 화재 전파

불은 파티클이 직접 옆 칸을 태우는 식으로 만들지 않았습니다. 먼저 셀 데이터의 온도, HP, 상태를 바꾸고, 화면의 불꽃은 그 상태를 따라가게 했습니다.

구현 방식:

- `FireGridSimulator`가 2D 그리드 셀을 만들고 각 셀의 상태를 관리합니다.
- 셀은 `Normal`, `Burning`, `BurnedOut` 상태를 가집니다.
- 매 틱마다 불타는 셀만 순회합니다.
- 인접 셀의 온도를 올리고, 재질별 점화 확률에 따라 새 셀을 점화합니다.
- 물, 돌, 기름 같은 재질은 HP, 열 흡수, 점화 확률이 다르게 동작합니다.

처리 포인트:

- 전체 셀을 매번 검사하지 않고 `activeCells`만 갱신해 큰 그리드에서 비용을 줄였습니다.
- 한 틱 안에서 같은 셀이 여러 번 점화되지 않도록 `pendingIgnitions`에 모았다가 마지막에 적용했습니다.
- 물처럼 타면 안 되는 셀은 모든 점화 경로에서 먼저 걸러냅니다.

정리:

- 게임 룰은 셀 데이터가 담당하고, VFX는 결과만 보여주는 편이 다루기 편했습니다.
- 재질별 반응을 한곳에 모아두면 밸런스 값을 바꾸기 쉽습니다.

확장 방향:

- 바람 방향, 비, 물 스킬 같은 외부 조건을 셀 온도 계산에 더할 수 있습니다.
- 멀티플레이에서는 전체 파티클이 아니라 셀 상태 변경만 동기화하는 쪽이 가볍습니다.

### 3. 복셀 건물 파괴

정형 건물이나 벽은 격자로 다루면 파괴 위치와 남은 구조를 계산하기 쉽습니다. 이 데모에서는 건물을 3차원 셀 배열로 만들고, 폭발 반경 안의 셀 HP를 깎은 뒤 끊어진 덩어리를 별도 청크로 분리합니다.

구현 방식:

- `VoxelDestructibleBuilding`이 폭, 높이, 깊이를 가진 셀 배열을 생성합니다.
- 폭발 지점과 거리 감쇠를 이용해 셀마다 다른 데미지를 줍니다.
- HP가 0 이하인 셀은 제거하고 작은 디브리를 생성합니다.
- 남은 셀 중 지면과 연결되지 않은 그룹은 BFS로 찾아 청크로 분리합니다.
- 살아 있는 셀의 내부 면은 그리지 않고, 바깥으로 드러난 면만 메시로 만듭니다.

처리 포인트:

- 폭발 한 번에 생기는 디브리 수, 청크 수, 콜라이더 수에 상한을 뒀습니다.
- 작은 분리 그룹은 굳이 청크로 만들지 않고 디브리처럼 처리합니다.
- 청크 콜라이더도 모든 셀에 붙이지 않고 외곽 셀 중심으로 제한했습니다.

정리:

- 복셀 파괴는 평균 프레임보다 큰 폭발 한 번의 비용이 더 중요했습니다.
- 셀 크기는 곧 게임 룰의 단위가 됩니다. 셀이 크면 명확하고, 작으면 보기 좋지만 비용이 늘어납니다.

확장 방향:

- 큰 건물에는 영역별 메시 재빌드나 Job/Burst 처리를 붙이는 편이 좋습니다.
- 네트워크 게임에서는 깨진 셀 좌표만 변경분으로 보내는 구조가 잘 맞습니다.

### 4. 구조 응력 붕괴

다층 구조물은 HP가 0이 됐다고 바로 전체가 사라지면 어색합니다. 이 데모에서는 기둥이 받는 하중을 계산하고, 기둥이 무너지면 그 하중을 주변으로 넘긴 뒤 층이 순서대로 떨어지게 만들었습니다.

구현 방식:

- `StressCollapseBuilding`이 층과 기둥 배열을 관리합니다.
- 각 기둥은 현재 하중, 강도, 실패 여부를 가집니다.
- 기둥이 실패하면 남은 기둥에 하중을 다시 나눕니다.
- 강도를 넘긴 기둥은 붕괴 큐에 들어갑니다.
- 층을 지탱하는 기둥이 부족해지면 Rigidbody를 활성화하고 힘과 토크를 줍니다.
- `StressVisualizer`와 `StressCollapseHud`가 하중 상태를 색과 텍스트로 보여줍니다.

처리 포인트:

- 모든 붕괴를 한 프레임에 처리하면 건물이 갑자기 사라지는 느낌이 났습니다.
- `pillarFailToCollapseDelay`와 `cascadeDelayPerLayer`로 조금씩 처리해 무너지는 순서를 확인할 수 있게 했습니다.
- 층이 위로 튀지 않도록 upward 값을 낮추고 옆 방향 힘과 회전 성분을 섞었습니다.

정리:

- 붕괴 연출은 계산 정확도만큼이나 "순서가 보이는지"가 중요했습니다.
- 큐로 나눠 처리하면 카메라 흔들림, 먼지, 사운드 타이밍을 맞추기 쉽습니다.

확장 방향:

- 보스전, 폭파 미션, 컷씬처럼 카메라 연출과 함께 쓰기 좋습니다.
- 더 사실적인 구조 해석이 필요하다면 별도 물리 모델이 필요하지만, 게임 연출용으로는 현재처럼 단순한 하중 그래프가 다루기 쉽습니다.

### 5. 빔 소프트바디 차량

차량 데미지는 실제 자동차 시뮬레이션처럼 만들면 비용이 커집니다. 이 데모에서는 차체를 적은 수의 노드와 빔으로 나누고, 충돌 시 노드 위치와 빔 길이가 조금씩 변하도록 만들었습니다.

구현 방식:

- `BeamSoftBodyVehicle`이 노드, 빔, 패널 데이터를 관리합니다.
- 빔은 rest length, stiffness, damping, yield, break 값을 가집니다.
- `FixedUpdate`에서 여러 번 작은 스텝으로 나눠 빔 제약을 풉니다.
- 충돌은 `BeamSoftBodyCrashHandler`가 속도와 위치를 읽어 `ApplyImpact`로 전달합니다.
- `BeamSoftBodyMeshDeformer`는 노드 변화에 맞춰 차체 메시를 변형합니다.

처리 포인트:

- 한 번에 큰 힘이 들어오면 스프링이 튀기 쉬워서 solver iteration, displacement clamp, drag를 같이 사용했습니다.
- yield를 넘으면 빔 rest length를 조금 바꿔 찌그러진 상태가 남도록 했습니다.
- break를 넘은 빔은 끊어서 더 이상 힘을 전달하지 않게 했습니다.

정리:

- 차량 변형은 정확한 충돌 해석보다 "부딪힌 곳이 눌리고, 다시 어느 정도 남는 느낌"이 중요했습니다.
- 주행 물리와 손상 표현을 분리해 두면 조작감이 크게 흔들리지 않습니다.

확장 방향:

- 멀티플레이에서는 차체 변형을 전부 동기화하기보다 HP나 조작성 같은 게임 룰만 동기화하는 편이 현실적입니다.
- 차량 외형이 늘어나면 노드/빔 세팅을 ScriptableObject나 에디터 도구로 빼는 것이 좋습니다.

### 6. 런타임 메시 슬라이싱

검이나 레이저로 오브젝트를 자르는 연출은 미리 준비한 파편만으로는 만들기 어렵습니다. 이 데모에서는 입력으로 만든 평면을 기준으로 메시를 두 개로 나누고, 잘린 단면을 새 폴리곤으로 채웁니다.

구현 방식:

- `SliceController`가 마우스 드래그나 클릭으로 절단 평면을 만듭니다.
- `SliceTarget`이 붙은 오브젝트만 슬라이스 대상으로 삼습니다.
- `MeshSlicer`가 삼각형을 순회하며 평면 기준으로 위쪽/아래쪽 메시를 나눕니다.
- 평면과 걸치는 삼각형은 교차점을 계산해 새 삼각형으로 쪼갭니다.
- `CapBuilder`가 잘린 모서리를 모아 단면을 채웁니다.
- 결과 오브젝트에는 Rigidbody와 BoxCollider를 붙여 떨어지게 합니다.

처리 포인트:

- 평면 위에 정확히 놓인 정점은 NaN이 생기기 쉬워 epsilon 처리를 넣었습니다.
- upper와 lower의 cap 노멀과 와인딩을 반대로 둬 단면이 서로 마주 보게 했습니다.
- 원본이 여러 머티리얼을 쓰는 경우 기존 서브메시는 유지하고 cap 머티리얼만 마지막에 추가했습니다.

정리:

- 슬라이싱은 자르는 것보다 잘린 면을 자연스럽게 막는 일이 더 중요했습니다.
- 복잡한 외부 메시를 모두 처리하기보다, Read/Write 가능한 단순한 메시를 대상으로 제한했습니다.

확장 방향:

- 오목한 cap이나 복잡한 non-manifold 메시까지 안정적으로 처리하려면 더 강한 폴리곤 재구성 로직이 필요합니다.
- 칼 게임으로 확장한다면 슬로모션, 슬래시 라인, 단면 셰이더를 더 다듬는 쪽이 효과가 큽니다.

| 짧은 반응 | 맞았을 때 바로 반응이 보여야 함 | 데칼, 먼지, 파편, 카메라 흔들림을 데미지와 함께 처리 |
| 비용 관리 | 파괴 오브젝트가 많아지면 물리 비용이 커짐 | 디브리, 청크, 콜라이더, 투사체 수에 상한 설정 |
| 연출 순서 | 붕괴가 한 번에 끝나면 무게감이 약함 | 큐와 지연 시간으로 단계적으로 처리 |
| 데이터 분리 | 파티클만으로 게임 룰을 만들면 확장이 어려움 | 화재, 복셀, 응력은 데이터 상태를 먼저 갱신 |
| 외부 에셋 | Built-in 머티리얼이 URP에서 깨질 수 있음 | URP 머티리얼 보정 헬퍼와 에디터 메뉴 사용 |
| 재사용 | 입력 방식이 바뀌어도 시스템을 다시 짜지 않기 | `TakeDamage`, `ApplyExplosion`, `ApplyImpact`, `TrySlice` 같은 진입점 유지 |

## 주요 튜닝 값

| 값 | 현재 의도 | 너무 작을 때 | 너무 클 때 |
| --- | --- | --- | --- |
| 파편 수명 | 파괴 후 장면 정리 | 파괴감이 짧게 끝남 | 씬에 Rigidbody가 오래 남음 |
| 화재 틱 간격 | 전파 속도와 CPU 비용 조절 | 불이 너무 빠르게 번짐 | 반응이 답답해 보임 |
| 복셀 셀 크기 | 건물 파괴 해상도 결정 | 셀 수가 늘어 비용 증가 | 파괴가 큼직하고 단순해짐 |
| 청크 최대 수 | 분리된 덩어리 물리 비용 제한 | 큰 덩어리가 잘 안 떨어짐 | Rigidbody와 Collider가 많아짐 |
| 붕괴 지연 시간 | 층이 무너지는 순서 조절 | 한 번에 사라지는 느낌 | 연출이 늘어져 보임 |
| 빔 solver iteration | 차량 변형 안정성 | 스프링이 튀거나 떨림 | CPU 비용 증가 |
| 슬라이싱 epsilon | 평면 위 정점 처리 | cap 깨짐, NaN 가능 | 절단 위치가 둔하게 느껴질 수 있음 |

## 트러블슈팅

| 문제 | 원인 | 해결 | 정리 |
| --- | --- | --- | --- |
| 파편이 거의 움직이지 않음 | 폭발 힘에 위쪽 성분이 부족함 | upwardsModifier와 보조 방향 힘을 추가 | 파괴는 힘 방향만 조금 바뀌어도 느낌이 달라짐 |
| 불이 한 틱에 과하게 번짐 | 새로 붙은 셀이 같은 틱에서 다시 전파됨 | `pendingIgnitions`에 모은 뒤 틱 마지막에 적용 | 상태 전이는 한 번에 모아 처리하는 편이 안전함 |
| 물 셀이 가끔 타는 것처럼 보임 | 점화 진입 경로가 여러 곳으로 나뉨 | 모든 점화 경로에서 `CanBurn`을 먼저 검사 | 예외 재질은 입구에서 막아야 함 |
| 폭발 후 프레임이 크게 튐 | 디브리와 청크가 한 번에 많이 생김 | 생성 수와 콜라이더 수에 상한을 둠 | 파괴 시스템은 최악의 한 번을 기준으로 봐야 함 |
| 건물이 한 프레임에 무너짐 | 실패한 기둥을 즉시 모두 처리함 | 붕괴 큐와 delay로 단계 처리 | 무너지는 순서가 보여야 무게감이 생김 |
| 차량 노드가 튀거나 떨림 | 스프링 보정량이 한 스텝에 너무 큼 | substep, clamp, drag 적용 | 소프트바디는 안정화 장치가 먼저 필요함 |
| 슬라이싱 cap이 뒤집히거나 비어 보임 | cap 와인딩과 노멀 방향이 섞임 | upper/lower cap 방향을 분리 | 절단 결과는 단면 품질이 가장 먼저 보임 |
| URP에서 머티리얼이 분홍색으로 보임 | Built-in 셰이더 참조가 남아 있음 | `UrpMaterialFixer` 계열 헬퍼로 교체 | 반복되는 머티리얼 수정은 도구화하는 편이 낫다 |

## 개발 메모

- 파괴 연출은 시뮬레이션 하나로 끝나지 않았습니다. 데미지, 상태 변화, 이펙트, 사운드, 카메라 반응이 함께 있어야 결과가 자연스러웠습니다.
- 작은 오브젝트는 사전 분할 파편이 가장 관리하기 쉬웠고, 구조물은 격자나 하중 그래프처럼 데이터 단위를 먼저 잡는 편이 좋았습니다.
- 화재와 복셀은 전체를 매번 검사하지 않고 변한 부분만 처리하는 구조가 중요했습니다.
- 응력 붕괴는 정확한 구조 계산보다 순서와 타이밍이 더 크게 느껴졌습니다.
- 차량 변형과 메시 슬라이싱은 경계 케이스가 많아, 데모에서 허용할 대상과 범위를 먼저 정하는 것이 필요했습니다.
- 외부 에셋을 섞는 프로젝트에서는 URP 머티리얼 보정 같은 작은 도구가 생각보다 시간을 많이 줄여줍니다.

## 에셋 및 라이선스

공개용 저장소에는 직접 작성한 코드, 데모 씬, 샘플 머티리얼, 래퍼 프리팹을 중심으로 포함했습니다.

포함하지 않은 항목:

- Asset Store에서 내려받은 원본 패키지와 import 결과물
- 대용량 FBX, 텍스처, 사운드, VFX 원본
- Unity `Library`, `Temp`, `Logs`, `UserSettings` 같은 로컬 생성 파일
- 개인 작업 메모와 로컬 검증 파일

일부 씬이나 프리팹은 로컬 외부 에셋 GUID를 참조할 수 있습니다. 새로 클론한 환경에서는 모델, VFX, 사운드 연결이 비어 보일 수 있지만, 핵심 구현 코드는 `Assets/Scripts`와 `Assets/Slicing`에서 확인할 수 있습니다.

자세한 제외 기준은 `docs/asset-policy.md`에 정리했습니다.

## 현재 한계와 다음 개선

- `docs`에는 현재 Fire, Impact, Voxel, Stress 네 개의 GIF만 있습니다. Beam Soft-Body와 Mesh Slicing 캡처는 아직 추가하지 않았습니다.
- 복셀 건물은 데모 규모를 기준으로 만들었고, 수만 셀 규모의 큰 건물을 바로 처리하는 구조는 아닙니다.
- 메시 슬라이싱은 Read/Write가 가능한 비교적 단순한 메시를 대상으로 가정합니다.
- 네트워크 동기화 코드는 포함되어 있지 않습니다.
- 일부 외부 에셋 머티리얼은 자동 URP 보정으로 처리되지 않아 수동 교체가 필요할 수 있습니다.
- 튜닝 값은 코드와 Inspector 중심이라, 장기적으로는 ScriptableObject나 별도 데이터 테이블로 옮기는 편이 좋습니다.

## 핵심 설계 결정

- 작은 파괴 오브젝트는 런타임 절단 대신 사전 분할 파편 교체로 처리했습니다.
- 화재는 파티클 중심이 아니라 셀 데이터 중심으로 만들었습니다.
- 복셀 파괴는 디브리, 청크, 콜라이더 수에 상한을 둬 폭발 한 번의 비용을 제한했습니다.
- 응력 붕괴는 큐와 지연 시간을 사용해 무너지는 순서가 보이도록 했습니다.
- 차량 변형은 풀 소프트바디 대신 적은 수의 노드와 빔으로 눌림과 손상만 표현했습니다.
- 메시 슬라이싱은 원본 서브메시를 유지하고 잘린 단면만 별도 머티리얼로 추가했습니다.
- 외부 destruction 라이브러리 없이 Unity 기본 물리와 Mesh API 위에서 동작하도록 구성했습니다.
